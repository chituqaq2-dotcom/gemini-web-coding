# 07 实战经验（按主题整理）

我们自己真实用下来的结论，和网上说法不一致时以这里为准。按主题归类，同类合并；新结论放进对应主题，过时的直接改掉。具体坑和报错见 [05](05-踩坑记录.md)，每个任务的额度见 [08](08-任务账本.md)。

## 1. 部署（2026-11-23）
- **从零到能用约 3 小时**，大部分时间花在装 WSL、下镜像、等重启；配置本身不难。
- **交给本地 agent（Codex CLI）执行最省心**，体验取决于提示词的停止规则：
  - 写“报错就停”→ 第一步就停，来回问。
  - 写“小问题自己修、事后汇报，只在 重启 / 密码 / token / 删数据 / 加挂载 时停”→ 全程只停 4 次（重启、建 Linux 用户、输 runabout 密码、填隧道 token），都是必须本人来的。
- **密码和 token 全程不经过任何 AI**：Linux 用户在自己终端建，runabout 密码用脚本自己输两遍只存哈希，隧道 token 自己用 nano 粘进 `.env`。
- 国内网络两个必做：`.wslconfig` 开 `networkingMode=mirrored` 让 WSL 走 Windows 代理；Docker 构建换国内 Debian 源。
- **容器没外网的真因**（11-24）：WSL 有代理变量，容器没有（Compose 只给构建配了代理）；Windows 代理只听回环端口，容器连不到。加一个代理转发服务再注入代理变量解决。报 PERMISSION_DENIED 不一定是权限，先看容器里有没有代理。
- **Windows 仓库从 Linux 侧读一律先设换行**（11-24）：仓库 core.autocrlf=true 而容器 git 没设，5696 个文件全显示修改、`git status` 28 秒。用 GIT_CONFIG_COUNT 环境变量给容器设 autocrlf 后 1 行、2 秒。

## 2. 接入 Gemini 与模式选择（2026-11-23）
- Connected Apps 藏在 **Personal Intelligence** 里；**名字保存前改成英文短名**（`runabout`），忘了只能删掉重加；Client ID / secret 留空自动注册。
- **Chat 模式能调 `@runabout`**，和 Task 一样好用（网上“开 Task 才能连 MCP”在我们这里不成立）。思考强度只有 Chat 能调（有 high），Task 不能调。日常用 Chat；Task 留给交代完让它自己跑的长任务（能否跑更久待验证）。
- `@runabout` 必须从 @ 菜单点选成标签；手打的文字它可能不调工具、自己瞎答。

## 3. Gemini 的能力边界（实测）
- **只读分析质量够用且细心**（11-23，Neon-high，10 GB 项目体积分析）：总表互不重叠、加总等于总体积；找到 78% 体积在被忽略的输出目录、`.git` 里 500 多 MB 中断残留临时包；守住“不按目录名判垃圾”，发现被 Git 追踪的子目录标为不可删；在“构建垃圾”里抓出加密数据库备份和私钥，明确“禁止整目录删”。不足：几十个历史目录合成一行“可删”粒度偏粗；个别恢复命令是通用的，没核对项目实际用法；Markdown 嵌套列表格式有些乱。
- **试验场写代码 + 自测已过关**（11-24～25，`_sandbox` 四轮，见 08）：
  - 从零建项目、`pnpm init/add`、写 vitest 测试并跑到全绿；
  - 测试失败时自己读报错、改代码、重跑（不给任何提示也能修好，最多 3 次重试的约束它会遵守）；
  - 在已有项目里原地跨文件编辑（不重建文件），一次全绿；
  - 预埋 bug（分页 0/1 起始页 + floor/ceil）它写测试自己测出两处并修对；
  - 没执行的命令会明说“未执行”，不编造输出。
  - 早期它曾把“命令被白名单拒”误报成“没挂工具”；提示词要求“贴出每个工具报错原文”后就如实了。
- **单轮约 13–15 次工具调用就到顶**（11-25 第六版实测；11-23 起多次遇到）：提示 `You have exceeded the maximum number of tool and search calls (0 remaining)`。进度不丢，同对话回一句“继续”即可（续跑那轮 3 次调用就收尾，成本很低）。原因之一：runabout 目前只暴露 read 和 shell，写文件只能一次一个 shell 调用。对策：
  - 提示词写“尽量少用工具调用”“把多步写成一个脚本跑”（11-23 清理任务实测：写成脚本后台跑 + 轮询，一次 Allow 搞定）；
  - 大任务先让它写分步清单，每轮做几步打勾；
  - 根治：runabout 加批量工具 write_files / read_files / run_commands（每项仍过原有校验和白名单），11-25 Codex 已写好代码，待测试和重启。

## 4. 额度
- **贵的是“分析 + high + 大量工具输出”**：10 GB 项目分析（high，3 次 Allow）用了 5 小时窗口 19%、周额度 1%；同规模的执行类任务（medium，照清单搬文件）约 5%；试验场写代码小任务（high）3–5%。周额度很宽，真正卡人的是 5 小时窗口。
- 设置页的 Always allow 和对话内弹窗是两套：设置页全选了，新对话里 shell 照样弹（见 05 第 20、24 条）；自动点击脚本见 05。
- 烧得快的原因：① 每点一次 Allow 算一轮，整段上下文重发，看手机慢了缓存还会过期；② high 思考本身贵；③ 长工具输出直接吃 token。对策：第一次弹窗就点 Always allow；读代码/统计用 medium、改代码/难 bug 用 high；提示词加 `Keep command output short (pipe through sort | head).`
- **新对话 vs 原对话续做**：新对话小型复核 6%，原对话续做一条删除 5%，差不多。按任务边界开新对话即可，不必为省额度刻意拆或硬留。
- **读数会滞后、会缓存**：任务结束后读数可能几分钟到十几分钟才更新（11-23 有一次 14 分钟）；读数比上次低就是旧值，作废。读法见 [09](09-用户习惯.md) 末节：先读一次，不变就每 3 分钟再读，最多 30 分钟。
- **额度自动读取已实现**（11-24）：用户浏览器的油猴脚本打开 usage 页就把读数推到一个带密钥的小接口（Cloudflare Worker + KV），任何 agent 用只读地址 `GET <地址>/latest?k=<READ_KEY>` 读，返回 5 小时 %、每周 %、读数时间和重置时间。`read_at` 没变说明还没有新读数（用户没打开 usage 页），不是消耗为零。usage 页文字顺序不对称（5 小时块“% used”在“Resets”前，每周块相反），脚本按标题分块各自找。

## 5. 写提示词
- 英文写指令 + `Reply in Chinese.`；开头 `@runabout` 标签；写明模型、模式、思考强度、是否新对话。
- 精确写出文件名和路径；只跑指定的测试文件，不跑全量。
- 项目已有交接文档（AGENTS.md + docs/）就让 Gemini 读相关那几份，别另建 NOTES.md；把项目自己的禁区写进提示词（不写它很可能建议整目录删）。
- 删除永远两步走：先只读出表（路径、大小、是什么、能否删、怎么恢复）→ 人看完 → 单独发删除指令，先 mv 到仓库外回收目录，带 Git 追踪文件或私钥/备份的目录自动跳过。模板 prompts/task-disk-cleanup-step1.md。
- 试手类指令加三句：“命令失败自己读报错修、最多重试 3 次”“贴出每个工具报错原文”“尽量少用工具调用”。
- 接手后重发旧指令前，先查项目里的执行记录（11-23 Gravity 清理第三步其实已做完、没记进本仓库，接手 agent 又发了一遍，白跑 5 分钟）。

## 6. 与本地 agent（Codex）配合
- Windows 侧的测试、部署、浏览器实测交给 Codex 一条指令做完，比让用户粘 PowerShell 来回贴结果顺得多；Codex 还能自己开隔离浏览器验页面。
- **改 runabout 的节奏**：Codex 先在独立容器自测 → 停下问重启 → 重启后正式容器自测（smoke）→ Gemini 端用四项健康检查实测（出网、建/拷文件、git status、预期被拒的 rm，prompts/runabout-health-check.md）。重启会打断正在跑的 Gemini 任务，等 Gemini 跑完再重启。
- **白名单要实测 Gemini 常用写法**（11-24）：白名单曾把 `curl -w "%{http_code}"` 的花括号当 shell 展开误拒，复合命令整条不执行，Gemini 页面一直显示 Connecting（服务端 3ms 就拒了）。Gemini 卡在 Connecting 或说“没工具”，先让 Codex 查 runabout 日志：请求到没到、是不是被拒。
- **runabout 本地有自己的提交后**，升级不能 `git pull --ff-only`，改成 fetch + rebase（写在 runabout 的 deploy/WORKSPACE.md）。
- **长任务慢多半不怪模型**（11-24 跑了一下午）：每几分钟停下等“继续”、撞模型满载；建镜像和全量测试每次几分钟；验收标准写错（把子集数字当全量），模型反复追原有失败。教训：测试验收写成“只对比新环境独有的失败，全量最多跑 N 次”，先确认测试规模再写数字。
- **别跨层套引号**：从 PowerShell 套 `wsl bash -lc` 引号反复被吃；Windows 侧命令在 PowerShell 跑，Linux 侧在 WSL 跑，复杂的写成脚本文件。指令里写“同一步连续失败两次就停下汇报”。
- Codex 会拒绝“报假标记”（两次拒绝把 shell 的 OpenWorldHint 改成 false，理由是会误报工具能力）；这类改动用户自己跑命令最快。
- Codex（GLM）偶尔在回报末尾冒出一句无关乱码（11-25 出现“去过 Congo，现在住在法国？”），忽略即可，不代表做了别的事。
- 网络下载类步骤（Go 工具链、Node 层）在国内容易半截断（curl 18）；优先用本机已有镜像或国内代理源，不要反复重下。

## 7. 清理与验收
- **清理收尾好流程**（11-24 newapi，10 项 205 MiB 一次过）：Codex 只读盘点出带编号的表（改了什么、主线里有没有、未推送数、大小、建议）→ Hark 给勾选建议 → 用户一句“可以” → Codex 挪进回收目录、写 MANIFEST、prune worktree、对比 git status 前后。同盘移动不释放空间，清空回收目录才算。
- **验收前先确认看的是哪个版本**：只部署 Worker 不等于前端更新；Gravity 网页是线上 gravity 分支的构建，网页里有 `__BUILD_BRANCH__`/`__BUILD_COMMIT__` 标记可读。验收本地改动要么本机起开发服务，要么先合并发布（11-23 天气白跑一轮）。
