# 07 实战经验（按时间记录）

这里记的是我们自己真实用下来的结论，和网上说法不一致的地方以这里为准。新经验按日期追加。

## 2026-11-23 · 第一天：部署到第一个任务

### 部署
- **从零到能用约 3 小时**，大部分时间花在装 WSL、下载镜像、等重启上；配置本身不难。
- **交给本地 agent（Codex CLI）执行最省心**，但提示词的“停止规则”决定体验：
  - 写“报错就停”→ 第一步就停，来回问，很烦。
  - 改成“小问题自己修、事后汇报，只在 重启 / 密码 / token / 删数据 / 加挂载 时停”→ 一路顺下来，只停了 4 次（重启、建 Linux 用户、输 runabout 密码、填隧道 token），每次都是必须你本人来的。
- **密码和 token 全程没经过任何 AI**：Linux 用户在你自己的终端建，runabout 密码用脚本让你自己输两遍只存哈希，隧道 token 你自己用 nano 粘进 `.env`。这样做多花几分钟，但心里踏实。
- 国内网络两个必做：`.wslconfig` 开 `networkingMode=mirrored` 让 WSL 走 Windows 代理；Docker 构建换国内 Debian 源。

### 接入 Gemini
- Connected Apps 藏在 **Personal Intelligence** 里，第一次找了半天。
- **名字一定在保存前改成英文短名**（`runabout`），我们忘了改，只能删掉重加。
- Client ID / secret 留空就行，自动注册。

### Chat 还是 Task（实测）
- **Chat 模式能调 `@runabout`**，和 Task 一样好用。网上有人说“开 Task 才能连 MCP”，我们这里不成立。
- **思考强度只有 Chat 能调**（有 high），Task 不能调（社区猜固定 medium）。
- 结论：**日常用 Chat**，按活选强度；Task 留给交代完就让它自己跑完的长任务。

### 第一个任务的额度账
- 任务：用 Neon-high 分析一个 10 GB / 8 万文件的项目为什么这么大（只读）。
- 发出去后**连着弹了 3 次 Allow**（shell kill、执行 shell 命令 ×2）。连接时已经在设置里选了 Always allow，但第一次调用每个工具仍会弹窗。
- 结果：跑到一半 **5 小时窗口 12%**，整个任务跑完 **19%**，**周额度始终 1%**。粗算一个中等分析任务 ≈ 5 小时窗口的两成，5 小时内能做 4–5 个这样的任务。看着 5 小时那条涨得快会慌，其实周额度才是长期上限，5 小时窗口到点就重置。
- 烧得快的原因：
  1. 每点一次 Allow 都算一轮新对话，整段上下文重发；你看手机慢一点，缓存还会过期。
  2. high 思考本身贵。
  3. 统计 8 万个文件的工具输出很长，直接吃 token。
- 对策：
  - 每个工具第一次弹窗就点 **Always allow**，之后不再问。
  - 读代码、分析、统计用 **medium**；改代码、查难 bug 再开 high。
  - 提示词加 `Keep command output short (pipe through sort | head).`

### Neon-high 网页版的工作质量（第一个任务实测）
任务同上：只读分析一个 10 GB 项目的体积构成，出一张“能不能删”的表。

做得好的：
- **数字对得上**：总表各项互不重叠，加起来正好等于总体积；“可删”“需重建”两档的小计我复算过，误差在四舍五入内。
- **找到了人没想到的大头**：项目体积 78% 在一个被忽略的输出目录里（几十份重复构建快照和旧安装包），还有 `.git` 里 500 多 MB 的中断残留临时包（`tmp_pack_*`），而真正的 Git 历史只有 240 MB，不需要重写历史。
- **守住了禁区**：提示词里写的“不按目录名判垃圾”它照做了，把输出目录拆成二十多项逐个判断；发现其中 4 个子目录其实被 Git 追踪（3D 资产），标成不可删。
- **抓到了危险文件**：在一批“构建垃圾”目录里发现夹着加密数据库备份和私钥，明确写“禁止整目录删”。这一条如果漏掉，后果最重。
- **该谨慎的地方谨慎**：失效 worktree 先确认提交都已合入；临时包提醒先确认没有后台 git 进程；旧安装包标“待确认”而不是“可删”。
- 每项都给了恢复方式，最后建议先做零副作用的两步。

不足：
- 把 34 个历史任务目录合成一行“可删”，粒度偏粗；真删之前仍应让它列出具体子目录清单，并再扫一遍有没有 `.private`/密钥类文件。
- 输出的 Markdown 嵌套列表格式有些乱，不影响阅读。
- 个别“恢复方式”是通用命令（比如 Python 虚拟环境的重建），没核对项目实际用法。

结论：**只读分析类任务，Neon-high 的质量够用，且相当细心**；代价约为 5 小时窗口的 19%。以后同类分析可试试 medium，看质量掉多少再定。删除动作仍然坚持两步走：先表，后人工确认，再单独发删除指令。

### 写提示词
- **项目已有交接文档就别另建 NOTES.md**：比如项目里已有 AGENTS.md + docs/，直接让 Gemini 先读相关的那几份。
- **把项目自己的禁区写进提示词**：我们的项目文档里写了“测试运行器依赖不按目录名判垃圾”“实验目录要逐文件判断”，不写进去 Gemini 很可能建议整目录删掉。
- 删除类任务永远**两步走**：先 READ-ONLY 出一张表（路径、大小、是什么、能否删、怎么恢复），你看完再单独发删除指令。
- 真删时**先 mv 到仓库外的回收目录**，带 Git 追踪文件或私钥/备份的目录自动跳过，确认项目能正常构建后再清空。模板见 prompts/task-disk-cleanup-step1.md。
- 英文写指令 + `Reply in Chinese.`；带 `@runabout`，不带时它可能不调工具自己答。

## 2026-11-23 下午：几条新结论
- **新对话 vs 原对话续做**：新对话做一个小型只读复核 6%，原对话续做一条删除 5%。读交接文件的开销不大，按任务边界开新对话即可。
- **本地 agent 会拒绝“报假标记”**：Codex 两次拒绝把 shell 的 `OpenWorldHint` 改成 false（理由：会误报工具能力）。这类改动由用户自己跑命令最快。
- **设置页 ≠ 对话内弹窗**：设置页保持 Always allow 后，新对话里 shell 照样弹确认。两者是分开的。
- **额度读数会缓存**：自动读取曾连续拿到旧值。读之前强制刷新、看到“Updated just now”；比上次低就作废。

## 想法：让所有 agent 都能读到额度（未实现）
Gemini usage 页要登录 Google，别的 agent 读不到。可行做法：在用户自己的浏览器装一个油猴脚本，打开 gemini.google.com/usage 时把两个百分比和时间 POST 到一个带密钥的小接口（例如 Cloudflare Worker + KV），接口提供只读的 JSON 地址给任何 agent 读。用户只需在任务前后各刷新一次那个页面。没做之前，就请用户发一句读数。
- **单轮工具调用有上限**（2026-11-23 16:01）：Gemini 一轮里调用工具次数到顶会自己停下，让你回一句“继续”。所以大任务拆成“启动后台 → 下一轮核对”很自然；回“继续核对结果”这种短句成本很低。
- **usage 页的文字顺序不对称**（2026-11-23，英文界面）：5 小时块是“`Current usage` → `7% used` → `Resets at 8:23 PM`”，每周块是“`Weekly limit` → `Resets Nov 25 at 4:23 PM` → `2% used`”。脚本要按标题分块再各自找 `% used` 和 `Resets`，不能假设先后顺序。

- 网页版单轮有工具调用上限（次数未公布），中等改动（十几个文件）要 2–3 轮。进度不丢，回“继续”即可。复杂任务：先让它在仓库写分步清单，每轮做几步打勾。Task 模式能否跑更久待验证。（2026-11-23 Gravity 天气）
- 接手后重发旧指令前，先查项目里的执行记录（如清理候选.md）：2026-11-23 Gravity 清理第三步其实已做完，没记进本仓库，接手 agent 又发了一遍，白跑 5 分钟（脚本“对不上就跳过”所以没误删）。
- 只部署 Worker 不等于前端更新：Gravity 网页是线上 gravity 分支的构建，刷新拿不到本地分支的改动。验收新前端要么本机起开发服务（Codex 起在 127.0.0.1:5173），要么先合并发布。（2026-11-23 天气，白跑一轮）
- Windows 侧的测试、部署、浏览器实测交给 Codex 一条指令做完，比让用户粘 PowerShell 来回贴结果顺得多；Codex 还能自己开隔离浏览器验页面。

## 2026-11-24：runabout 出网、白名单、清理收尾
- **runabout 没外网的真因**：WSL 里有代理变量，容器里没有（Compose 只给构建配了代理）；Windows 代理只听回环 7890，容器连不到。解法是加一个代理转发服务再注入代理变量。教训：报 PERMISSION_DENIED 不一定是权限，先看容器里有没有代理。
- **容器里 git status 慢/满屏修改**：Windows 仓库 core.autocrlf=true，Linux git 没设，5696 个文件全被当成修改，要 28 秒。用 GIT_CONFIG_COUNT 环境变量给容器设 autocrlf 后 1 行、2 秒。Windows 仓库从 Linux 侧读一律先查这个。
- **白名单要实测 Gemini 常用写法**：新白名单把 `curl -w "%{http_code}"` 里的花括号当成 shell 展开误拒，复合命令整条不执行，Gemini 页面一直显示 Connecting（服务端 3ms 就拒了，卡在 Gemini 前端）。“一直 Connecting”先让 Codex 查 runabout 日志，看请求到没到、是不是被拒。
- **改 runabout 的节奏**：Codex 先在独立容器自测 → 停下问重启 → 重启后正式容器自测 → Gemini 端用一条简单的四项健康检查实测（出网、建/拷文件、git status、预期被拒的 rm）。健康检查提示词见 prompts/runabout-health-check.md。
- **本地补丁和上游**：本地 main 有了自己的提交后，`git pull --ff-only` 升级会失败，要改成 fetch + rebase，并写进 runabout 的 deploy/WORKSPACE.md。
- **清理收尾的好流程**：Codex 只读盘点出带编号的表（改了什么、主线里有没有、未推送数、大小、建议）→ 我给勾选建议 → 用户一句“可以” → Codex 挪进回收目录、写 MANIFEST、prune worktree、对比 git status 前后。newapi 这一轮 10 项 205 MiB 一次过。同盘移动不释放空间，清空回收目录才算。
- **验收前先确认看的是哪个版本**：网页里有 `__BUILD_BRANCH__`/`__BUILD_COMMIT__` 标记，Codex 能读出来；Gravity 天气那次用户看的是线上旧版，白跑一轮。


### 2026-11-24 Codex 长任务跑了一下午的原因
- 慢主要不在模型：① 每跑几分钟就停下等“继续”，中途还撞模型满载，大半时间在空等；② 建镜像、跑全量测试每次都要几分钟；③ 验收标准写错（把天气子集“14 文件 136 条”当全量），模型反复跑全量追原有失败。
- 教训：给 Codex 的测试验收写成“只对比新环境独有的失败，全量最多跑 N 次”；先确认测试规模再写数字；换模型只能少停几次，提速靠改指令。
- 同日（GLM-5.3 接手后）：模型切换后 15 分钟干净推进；但 Windows 对照时从 PowerShell 套 `wsl bash -lc` 引号反复被吃（tr/paste 报 `"` 参数），还在 WSL 里跑 /mnt/d 当“Windows 对照”。教训：Windows 侧命令直接在 PowerShell 跑，Linux 侧直接在 WSL 跑，别跨层套引号；指令里写“同一命令连续失败两次就停下汇报”。
- **单轮上限约 13–15 次工具调用**（2026-11-25 试手第六版）：建 8 个文件 + 装依赖 + 跑两次测试就到顶，提示语是 `You have exceeded the maximum number of tool and search calls (0 remaining)`。runabout 目前只暴露 read 和 shell，写文件只能一次一个 shell 调用，所以特别费次数。对策：同对话回“继续”（续跑那轮 3 次调用就收尾）；根治是在 runabout 加批量工具（write_files / read_files / run_commands，每项仍过原有校验和 allowlist）。提示词里加一句“尽量少用工具调用”有用。
